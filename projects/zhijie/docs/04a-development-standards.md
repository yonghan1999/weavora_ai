# 织界开发规范

> 适用范围：织界项目所有开发工程师、开发自测人员、独立测试人员、代码评审者和参与交接的协作者。本文是 D 阶段的项目级执行规范，必须与已批准需求、原型、UI、架构、`04-development-plan.md` 及 `workflow/spec/ROLES.md`、`CONTRACTS.md`、`GIT.md` 一起使用。发生冲突时，已批准基线和工作流门禁优先。

## 1. 目标与不可违反的边界

织界采用多人协作和增量交付。每次变更必须可追踪、可验证、可回退，并能由新成员仅凭任务契约、文件、证据和文档继续工作。

以下规则是硬性要求：

1. 业务代码、自动化测试和运行脚本只放在项目 `workspace/`；工作流状态、审批、审计和执行证据只能由 CLI 维护，禁止手工编辑。
2. 一个变更只能服务一个任务或一个已登记缺陷；超出任务契约的需求必须先回到需求/架构评审，不能在实现中顺手扩大范围。
3. 任何“完成”都必须有真实命令和退出码证据。代码编译成功不等于功能验收通过，模拟数据、固定返回值、空实现、`TODO` 占位和 `SKIP` 不能作为核心能力证据。
4. 不把控制面或 Lighthouse 变成内容服务器。文字正文、文件名原文、头像和附件字节不得进入控制面 API、数据库、日志、备份或 Lighthouse 转发路径。
5. 不添加 Relay、SFU、TURN、服务器媒体存储或透明回退；内容、语音和游戏流量经客户端虚拟局域网直连，客户端无在线副本时必须显示“暂不可用”。
6. 不记录、提交或复制密码、验证码、令牌、私钥、邮箱密钥、原始聊天内容、原始文件名和未脱敏诊断数据。

## 1.1 专业工程师的工作方式

每位参与者都按以下顺序工作：**理解现状 → 明确目标 → 评估风险 → 设计最小改动 → 编码 → 真实验证 → 记录交接**。遇到不确定性时先查文档、代码、接口和运行证据，再提出假设；不得用猜测替代事实，也不得为了保持进度隐藏阻塞。

- **先读后写**：修改前阅读相关任务契约、批准基线、现有实现、测试和调用方；确认谁依赖这个接口以及失败会影响什么。
- **小而完整**：每次只解决一个可描述的问题，保持变更可审阅、可测试、可回退；不要把重构、顺手清理和新功能混在一起。
- **边界优先**：先定义权限、错误、超时、容量、并发、断线、重启和回滚行为，再实现主流程；安全和一致性不能依赖调用者自觉。
- **证据驱动**：结论必须来自当前代码树上的命令、日志、测试或人工走查；“应该可以”“本地没问题”和截图不能代替验证证据。
- **尽早暴露风险**：工具、设备、平台、性能或第三方依赖存在阻塞时立即记录并停止相关路径；不通过删测试、放宽限制或伪造数据制造绿色结果。
- **可维护优先**：选择团队容易理解、调试和替换的实现；引入依赖、抽象、缓存、并发或特权能力前，说明它解决的具体问题和退出方案。
- **对结果负责**：发现自己或他人的变更可能破坏安全、数据一致性或已批准范围时，立即暂停并报告；评审不是走形式，交接不是甩锅。

## 2. 开始编码前：任务准入

开发人员领取任务前必须在任务说明中确认：

- 任务 ID、所属批次、负责人和协作者；
- 关联 REQ/AC、已批准架构和依赖任务；
- 输入、输出、验收、测试命令和回退策略；
- 允许修改的目录和明确不应触碰的基线文件；
- 当前环境、工具版本、设备/网络/邮箱等外部前置条件。

任务契约不完整、依赖未完成、验收标准含糊或需要改变批准基线时，状态保持 `blocked`/`awaiting_retry` 并报告原因，不能用猜测补齐。开发人员不得直接编辑 `state.json`、`audit.jsonl`、`approvals/` 或 `tests/evidence/` 中的执行证据。

每个任务先写一个可审阅的最小设计说明：数据结构、接口边界、错误路径、并发假设、资源上限、日志字段、测试夹具和回退点。设计说明不替代架构审批；它只解释如何在已批准架构内实现。

## 3. 多人协作和批次工作法

项目按 `04-development-plan.md` 的 B0～B9 批次推进。一个批次内采用以下顺序：

```text
任务准入 → developer 编码与 task-run
→ self_tester 自测 → 缺陷修复与回归
→ test_engineer 独立测试 → 批次评审 → 下一批
```

- 一个任务有一名明确负责人；协作者负责范围必须写在交接记录中，不能出现“大家一起改”的无主文件。
- 开发人员不得把尚未完成的任务依赖偷偷合并进当前任务；需要共享接口时先提交契约/夹具，再按依赖关系推进。
- 每个批次结束必须记录：完成任务、代码树哈希、F/G 证据、开放/关闭缺陷、遗留风险、回退步骤和下一批准入条件。
- 缺陷修复优先回到发现它的批次。修复必须包含复现用例、最小代码变更和相关回归；不得删除失败证据或降低验收标准来“消除”缺陷。
- 同一执行者可以顺序承担 developer、self_tester、test_engineer，但必须分别从批准基线出发，使用不同角色和独立证据，不能把开发自测改名为独立测试。

Git 分支、提交格式、合并和推送边界遵循 `workflow/spec/GIT.md`。凡涉及业务代码、自动化测试代码、运行脚本、数据库 migration、协议实现或配置行为的开发，必须先创建对应 Git 任务分支，禁止直接在 `develop` 上编码。仅限开发计划、规范、评审记录等文档维护时，才可按现有规则直接在 `develop` 上提交。

任务分支规则：

- 分支从最新且干净的 `develop` 创建；创建前核对当前分支、工作区差异和任务基线，不能把其他人的未提交改动带入分支。
- 一个分支只承担一个任务或一个缺陷；强关联且已登记为同一交付单元的任务才可共用分支。分支名使用 `feature/TASK-xxx-short-summary` 或 `fix/DEF-xxx-short-summary`。
- 分支创建后，任务负责人、关联 REQ/AC、允许修改范围和回退点写入交接记录。分支上的每个 commit 仍保持单一逻辑变更，不能用分支代替测试或评审。
- 任务分支必须完成 developer、self_tester 和适用的 test_engineer 检查后，才能合并到 `develop`；合并前检查依赖、代码树哈希、证据和冲突，禁止静默覆盖任一侧。
- 未完成、失败或待验证分支可以保留用于修复，但不得把它表述为已集成、已发布或已验收；分支删除、改写历史和合并到 `main` 仍需遵守授权边界。

任务分支的首个工作项必须是“现状与方案记录”：列出已阅读的文件、调用关系、风险、最小改动面、验证命令和回退点。没有这份记录，不能开始大范围编码。

用户已明确授权本项目在开发过程中由 AI 主动进行小步本地提交，因此 AI 可以在满足下列条件时自行提交，无需逐次询问：

- 提交只包含一个逻辑变更，通常是一个任务、一个缺陷修复或一项规范/文档维护；不把无关工作区改动带入提交。
- 适用的格式、类型检查、单元/集成测试和 `git diff --check` 已真实通过；无法运行的检查必须在提交说明或交接记录中标为未验证。
- 提交说明使用 `<type>(<scope>): <summary>`，只描述实际完成的内容；未完成或待验证工作使用 `wip:`，不得伪装成完成节点。
- 提交前核对 `git status`、暂存差异、秘密扫描和当前任务/批次状态；提交后记录提交号和文件清单。

该授权只覆盖本地 commit，不包含远程 push、合并到 `main`、改写历史、删除分支、标签或生产发布。AI 不得使用 `--no-verify`、强制推送、硬重置或覆盖他人提交。小步提交仍不能替代 E/F/G 阶段证据和批次出口。

## 4. 目录与模块边界

实现阶段按职责建立目录，目录名应稳定、可搜索，禁止按个人姓名或临时实验命名：

| 目录 | 职责 | 禁止事项 |
| --- | --- | --- |
| `workspace/control-plane/` | Java 控制面、事务、授权、Outbox、审计和控制 API | 接收正文/附件字节，提供任意上传或代理 |
| `workspace/lighthouse/` | Lighthouse 发现和打洞协调 | 业务转发、内容缓存、媒体存储 |
| `workspace/helper/` | 客户端 Nebula、作用域 Gate、活动 TUN 和受控 IPC | 任意 shell、任意路由、通用客户端中继 |
| `workspace/desktop/` | Electron/React/TypeScript 呈现、状态和窄 preload | 直接读本地内容路径、持有特权密钥、绕过 IPC |
| `workspace/workers/` | 非特权媒体探测和音频 Worker | 外网访问、管理员权限、执行不受控文件内容 |
| `workspace/protocols/` | 版本化 schema、错误码、信封和兼容规则 | 与某个 UI 页面私有耦合 |
| `workspace/tests/` | 可重复的契约、集成、系统和回归夹具 | 只断言文件存在或固定 JSON |
| `workspace/ops/` | 本地开发、测试拓扑、迁移和发布辅助脚本 | 自动执行生产部署或修改生产数据 |

模块通过窄接口通信。控制事务、网络授权、内容存储、媒体探测、音频和 UI 状态各自负责单一职责；不要为了“方便”共享数据库连接、全局可变状态、内部对象或管理员 IPC。

## 5. 代码质量和语言约定

### 5.1 通用规则

- 优先可读、直观、可测试的实现；先解决当前任务，不预留未批准的插件系统、服务集群或通用框架。
- 函数只做一件事，控制嵌套和隐式副作用；公共接口明确输入、输出、错误和超时。
- 不复制加入/授权/幂等/信封/错误码逻辑；先复用领域服务或纯函数，再扩展策略接口。
- 所有外部输入都做长度、格式、权限、作用域、代次、时间和资源上限校验；内部对象也不默认可信。
- 错误必须可分类、可观测、可恢复；禁止吞异常、返回空成功、打印堆栈中的秘密或用重试掩盖永久失败。
- 注释解释原因、约束和安全边界，不重复代码；协议和安全注释使用简体中文，代码标识使用英文。

### 5.2 Java 控制面

- 目标按架构固定为 Java 21 LTS；版本和 Maven Wrapper 由工具链任务锁定，不能使用本机 Java 8 偷换通过。
- 包名全小写；类/接口使用 `UpperCamelCase`，方法/变量使用 `lowerCamelCase`，常量使用 `UPPER_SNAKE_CASE`。接口按能力命名，避免无意义的 `*Util`、`*Manager`。
- Spring 模块只通过公开应用服务或端口交互。事务边界写在应用服务层，SQL/约束/索引变更必须有版本化 migration 和回滚说明。
- 对并发加入、资格、预算、撤销和 Outbox 使用显式锁序、幂等键和唯一约束；不能只依赖应用层“先查后写”。
- 使用 Spring Data JDBC/显式 SQL 时，查询列、排序、分页和锁意图必须清楚；禁止把正文、文件路径或任意 JSON 作为逃生字段写入控制面。
- DTO 只包含已批准的控制元数据；实体不能直接暴露给 API。密码、刷新凭据和密钥只存 hash/受保护引用，不进入日志。

### 5.3 TypeScript/Electron

- `strict` 类型检查必须开启；组件使用 `PascalCase`，变量/函数使用 `camelCase`，事件名使用明确动作，如 `leaseExpired`、`messageReceiptUpdated`。
- Renderer 只能调用窄 preload API；`contextIsolation`、sandbox、关闭 Node integration 和严格 CSP 不得为调试关闭后提交。
- 不在 Renderer 直接访问文件系统、命令行、网络 socket、凭据或任意 URL；路径、导航、IPC 方法和参数均采用白名单。
- 状态机显式表示 `pending`、`syncing`、`partial`、`available`、`unavailable`、`revoked`、`failed` 等状态，禁止用布尔值组合出互相矛盾的 UI。
- UI 的成功提示必须来自真实异步结果；按钮 busy、取消、超时、失权和焦点顺序必须可测试。

### 5.4 Helper、Worker 和原生依赖

- Nebula、音频、媒体探测等第三方版本、源码哈希、许可证和构建参数必须登记；禁止运行 PATH 中不受控的 `ffprobe`、脚本或未知二进制。
- Helper 只处理设备身份、加密传输、作用域 Gate、活动 TUN 和受控 IPC；解析内容、媒体和音频放在非特权 Worker。
- 任何特权操作都必须有创建者标记、最小权限和退出清理；崩溃、租约过期或签名无效时默认关闭 Gate 和路由。
- 原生内存、句柄、线程和子进程都有上限、取消路径和清理路径；失败不得留下可继续使用的旧授权、临时文件或管理员路由。

## 6. 接口、数据和网络规则

### 6.1 接口先行

公共 REST、WSS、IPC、Peer 帧和事件先更新版本化 schema、错误码和示例，再写实现。每个字段注明必填性、长度、默认值、敏感级别、兼容策略和失败码。未知字段、旧版本、错误 scope、错误代次、重放 nonce 和超限载荷必须有拒绝测试。

控制面只提供身份、群/房间、活动、授权、顺序、删除、逻辑预算、最小收据和审计接口；不得新增正文/文件上传接口或 `opaque payload` 逃生字段。

### 6.2 数据库与本机存储

- PostgreSQL 只保存控制元数据、最小收据、tombstone、资格和审计；每次 migration 可重复执行、有约束、有索引说明并在独立库演练回滚。
- SQLite/对象文件库采用 pending → 校验 → fsync/原子重命名 → 事务提交 → ACK 顺序；未持久提交不得报告已接收。
- 账号库、对象 ID、文件路径和临时文件必须隔离；对象名不使用发送方路径和原始文件名。磁盘满、崩溃、重复 ACK 和部分写入必须可恢复。
- 删除是 tombstone 和水位连续性的一部分；旧备份、旧游标或离线副本不得复活已删除内容或过期授权。

### 6.3 虚拟局域网和撤销

- 每个数据包/块/连接都经过当前资格、scope、活动/成员代次、源/目标和期限检查；已有连接跟踪和快速路径不能绕过 Gate。
- 文字、媒体、音频和游戏只走客户端虚拟局域网直连。明确禁用 Relay、SFU、TURN 和服务器内容缓存，不能因 NAT 失败暗加中继。
- 租约刷新采用保守单调时钟；迟到响应、墙钟倒退、休眠/唤醒、进程重启和控制面断连必须关闭 Gate 并重新同步。
- 控制面或 Lighthouse 在线不等于 Peer 可达；UI 必须区分“在线”“可达”“持有副本”“已接收”。

## 7. 测试和验证规范

每个任务至少包含成功、失败、边界、并发/重复、权限/作用域和恢复路径；涉及网络、落盘、音频、媒体或平台的任务必须安排真实或受控环境验证。

| 层级 | 必须检查 | 可替代范围 |
| --- | --- | --- |
| 静态/纯逻辑 | 格式、类型、schema、错误码、幂等和状态机 | 不能替代 I/O 或安全验证 |
| 单元测试 | 纯函数、策略、边界和错误映射 | 不能宣称 PostgreSQL/NAT/设备通过 |
| 控制集成 | 真实测试 PostgreSQL、migration、锁、Outbox、恢复 | 内存数据库只能做快速补充 |
| 客户端系统 | 双端真实虚拟 IP、Gate、TUN、Peer、撤销和重连 | 单进程 mock 不能替代 |
| 媒体/音频 | 接收端独立探测、字节完整性、持久化、真实或受控设备 | 发送端自检不能替代接收端检查 |
| UI/IPC | 真实异步状态、焦点、取消、权限和 Renderer 隔离 | 静态截图不能替代 |
| NAT/容量/平台 | 逐成员结果、16 人 60 分钟、Windows 及后续 macOS/Linux 实机 | 短演示、单机多进程和未测平台不得标通过 |

测试命令必须与任务登记命令逐字一致，由 CLI 记录证据。缺少工具、设备、证书、邮箱或平台时返回非零并标记“未验证”，不能把 skipped 当通过。代码改变后，受影响的 F/G/H 证据全部需要重跑。

## 8. 代码评审清单

评审者在批准合并或批次评审前逐项回答：

- 变更是否只覆盖一个任务/缺陷，是否追踪到 REQ/AC？
- 是否遵守控制面无正文、客户端直传、无中继和租约撤销边界？
- 输入校验、权限、scope、代次、超时、大小、速率和并发是否完整？
- 错误路径是否关闭资源、清理授权、避免重复提交和误报成功？
- 是否有 migration、兼容规则、回滚方案、日志白名单和秘密扫描？
- 单元测试之外，是否运行了该任务要求的真实集成/系统检查？未验证项是否明确写出？
- UI 是否来自真实状态，IPC/路径/导航是否白名单，是否会泄露本地文件？
- 是否新增不必要依赖、重复实现、全局状态、特权代码或未来范围？
- 代码、测试、文档和证据是否使用同一代码树哈希，工作区是否无临时文件和秘密？

评审者还必须确认作者先说明了现状和方案，变更经过最小化处理，关键失败路径和回退步骤可执行；若评审只能依赖作者口头解释或无法重现命令，退回补充证据。

评审意见必须指向文件和行号，按阻断、重要、一般、建议分级。阻断和重要问题关闭前，任务不能进入批次出口。

## 9. 交付、交接和变更记录

每个任务完成后，负责人提交以下交接信息：

```text
任务/缺陷：
关联 REQ/AC：
实际修改文件：
接口/数据库/配置变化：
运行命令与退出码：
证据路径与代码树哈希：
已验证范围：
未验证范围及原因：
已知风险与回退步骤：
下一位协作者的准入条件：
```

文档、代码、测试、制品和证据必须指向同一版本；不能只在聊天中交接。发现需求、架构、协议或安全边界需要变化时，停止当前任务并由技术负责人决定是否重新规划/重基线。任何生产部署、生产数据修改、密钥轮换和不可逆操作都不在本规范的默认授权内。

## 10. 违反规范时的处理

发现秘密泄露、服务器收到正文/附件、权限绕过、Relay 偷开、伪造测试证据、跳过独立测试或修改工作流状态文件时，立即停止相关批次，保留现场和失败证据，创建阻断缺陷并通知技术负责人。修复后必须进行安全复核、相关回归和必要的人类介入；不能通过删除日志、改写历史或降低验收标准结案。
