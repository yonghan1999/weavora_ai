# 织界需求重分析：100 人在线、游戏语音与单机资源

日期：2026-11-01
阶段：`B_REQUIREMENTS / in_progress`
性质：需求分析资料，尚未形成新的人工批准基线，也不代表已经完成容量、音质或跨平台验证。

## 一、结论先行

服务器为 2 核 CPU、2 GB 内存、Debian、5 Mbit/s 带宽，月流量 300 GB，额度不足时可以增加。基于此条件：

1. **100 人保持登录和在线状态**有较强可行性，但必须用真实负载测试确认。
2. **100 人同时多人语音并进行游戏网络通信**不能按现有 5 Mbit/s 直接承诺；瓶颈首先是瞬时带宽，其次是 2 GB 内存和 2 核 CPU 的资源争用。
3. 游戏语音优先采用客户端降噪、回声消除、自动增益和语音活动检测，质量必须通过真实设备和游戏并行场景验收。
4. Rust 适合承担客户端核心逻辑、音频接入边界、网络辅助进程和安全 IPC。界面沿用现有 UI 风格，Tauri、原生 Rust 或混合方案通过 PoC 决定。
5. 游戏网络中继由运营方策略控制：直连限定、直连优先并允许中继、强制中继均可评估；客户不选择线路。禁用中继且直连失败时，必须如实报告网络不可用。
6. 旧 Electron、Go、固定 SFU 和全量中继只能作为历史候选，不能未经验证进入架构基线。

## 二、已确认事实与边界

### 已确认

- 一台服务器：2 核 CPU、2 GB 内存、Debian。
- 瞬时带宽约 5 Mbit/s；月流量 300 GB，额度不足可增加。
- 初期目标尽量支持 100 人在线，最终以真实压测判断。
- 每房间最多 12 个账号，三平台仍是产品目标。
- 游戏时需要清晰人声和降噪，不能用降低码率掩盖音质问题。
- 团队熟悉 Rust，相对不熟悉 Go；客户端和本地网络逻辑优先评估 Rust。
- 网络中继由运营方选择，客户无感知；现有原型、UI、组件和视觉风格保留。

### 尚未确认但不阻塞分析

- 5 Mbit/s 是出网上限、入网上限，还是上下行共享上限。
- Debian 版本、地域和公网地址质量。
- 100 人在线时入房比例、同时发言人数、房间分布和代表游戏流量。
- 首批系统版本、客户端最低硬件和代表游戏。

以下按“5 Mbit/s 主要是服务器出网瓶颈”进行保守分析。

## 三、容量可行性

### 1. 月流量和瞬时带宽

5 Mbit/s 理论上约 625 kB/s。持续满速出网一天约 54 GB，一个月 300 GB 约支撑 5.6 天。增加月流量只能解决累计流量，不能解决语音、游戏中继和业务流量争用的峰值问题。

建议暂留 20% 链路余量，业务、语音、游戏和协议开销共同使用约 4 Mbit/s；该余量只是模型参数，必须用实测修正。

### 2. 语音转发模型

以下以每个发言者 32 kbit/s Opus 载荷做算术示例，不代表最终码率，也未计 RTP/UDP/IP、加密、FEC、重传和服务协议。一个房间有 `n` 名成员、`s` 名发言者时，SFU 出网约为 `s × (n - 1) × 每路码率`。

| 场景 | 纯音频出网估算 | 判断 |
| --- | ---: | --- |
| 1 房 12 人、1 人发言 | 352 kbit/s | 1×11×32，仍需计入协议和其他业务 |
| 1 房 12 人、2 人发言 | 704 kbit/s | 2×11×32，可作为首个 PoC 场景 |
| 1 房 12 人、12 人发言 | 4.224 Mbit/s | 12×11×32，已超过暂定4 Mbit/s共享预算；计协议和游戏流量后可能超过5 Mbit/s |
| 100人分成8个12人房和1个4人房，每房2人发言 | 5.824 Mbit/s | (8×2×11+2×3)×32，仅音频已超过5 Mbit/s |

容量必须分三档验收：

- **在线容量：**100 个账号登录、心跳、好友/群状态和有限消息同步。
- **活动容量：**明确多少人入房、多少人发言，分别测语音和游戏网络。
- **极限容量：**单房 12 人多人发言、游戏并行、直连/中继切换和权限撤销。

一档通过不能替代另一档通过。

用户本轮将单房上限由16人改为12人。边界为第12个不同账号可占额、第13个被拒，保留期账号仍占额；100人全站在线目标不变。以上数字均为重新计算的模型，不是压测结果。历史原始需求、旧复核记录、截图和可点击资产仍可能显示16人，不作为当前容量基线；可点击资产在新需求批准后的B1统一适配。

### 3. 服务器资源风险

2 GB 内存要覆盖 Debian、数据库、业务服务、WebSocket、监控、媒体或中继进程及缓存。旧方案把 Java 控制面、PostgreSQL、LiveKit 和 Java Relay 全放单机，不能直接视为可运行方案。

PoC 必须记录各进程峰值 RSS、CPU、连接数、GC/线程、数据库连接池、OOM 和重启恢复。禁止依靠持续 swap 掩盖内存不足，也不能把全部内存分给单个运行时。

## 四、游戏语音质量

### 目标

游戏时保持人声清楚、延迟稳定、多人可区分；键盘、风扇和游戏外放不应持续压过人声。语音失败和游戏网络失败分别呈现。

### 处理边界

- 优先客户端完成降噪、回声消除、自动增益/限幅、语音活动检测和静音不传输。
- 评估成熟 WebRTC 音频处理、Rust 原生库或绑定，不重写成熟编解码和 AEC。
- 覆盖耳机、扬声器、设备拔出、权限拒绝、游戏占用 CPU/GPU、多人叠音和弱网。
- 用同设备 A/B 录音和盲听记录清晰度、残留噪声、吞字、金属音、削波、啸叫、延迟和 CPU。

建议在安静、键盘、风扇、游戏外放和双人重叠发言场景边运行代表游戏边通话，再注入 1%/3% 丢包、20/50 ms 抖动。可暂以安静关键词听辨 95%、噪声场景 90%、正常网络口到耳 p95 200 ms 作为评审起点，正式门槛须经需求批准。

## 五、Rust 使用边界

| 范围 | 方向 | 需要验证 |
| --- | --- | --- |
| 客户端业务状态、连接编排 | Rust 优先 | 三平台线程模型、错误处理、UI IPC |
| 音频设备接入和本地处理 | Rust 优先评估 | 设备权限、AEC/降噪、延迟、CPU、许可证 |
| 虚拟网卡和网络辅助进程 | Rust 优先评估 | TUN/路由、权限、密钥保护、崩溃清理 |
| UI 展示 | 保持现有视觉风格 | Tauri、原生或混合方案的媒体与更新能力 |
| 控制面和数据服务 | 重新比较 | 2 GB 资源、团队维护和生态 |

建议先做 Rust 客户端核心加现有 UI 风格的垂直切片：登录、入房、真实音频设备、连接状态和退出清理。验证后再决定 UI 容器和网络辅助进程。

## 六、运营方控制的网络中继

候选模式：

1. **直连限定：**只允许直连，穿透失败就失败。
2. **直连优先、允许中继：**客户端自动尝试直连，失败后按服务端票据切换中继。
3. **强制中继：**运营方启用，用于受限网络或稳定路径。

策略先做全局配置。普通成员、群主和管理员不获得基础设施策略权限，客户端不提供拓扑选择开关。

必须定义：

- 服务端短期票据决定线路，客户端不能绕过禁用策略。
- 策略切换时明确已有连接立即断开、排空后切换或保持到活动结束。
- 游戏网络中继和语音媒体路径分别计量；禁用游戏中继不等于语音不经过媒体服务器。
- 直连失败且中继禁用时显示准确错误，不能偷偷中继或伪装成功。
- 失权、踢出、退房和删房时，直连与中继均须验证旧凭据、密钥和活动代次不能继续通信。
