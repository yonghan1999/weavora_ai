### 指定房间邀请：独立复测设计

开发侧已用无头浏览器登录受控 bridge，点击实际产品大厅的「邀请码加入」：出现「群邀请」列表和刷新按钮，弹窗可编辑字段数为 0，页面脚本错误数为 0。核对过本次 `dist/app.js`、`dist/src/views.js` 与对应源码的 SHA-256 一致。这复现了从玩家入口无法输入邀请码的缺口；未调用真实邀请服务，不是通过证据。

在专用测试群建两个可加入房间 A、B；列表首项为 A，邀请指向 B。用服务端活动成员与房间标识比对最终位置，不能仅凭客户端标题或“接受成功”提示判通过。以下是预期结果，不是执行证据。

| 场景 | 操作与判定 |
| --- | --- |
| 注册前获邀 | 先为首次玩家准备邀请，再用受邀邮箱注册。未验证时不能读房间或取得群籍；完成验证后仍能使用原邀请进入 B，无需邀请人重新搜索新账号。 |
| 已登录且不在该群 | 从邀请直接开始，最多一次确认；接受后只增加一条群成员关系，加入 B，A 的成员与活动不变。两个客户端重复接受，不重复建员或占位。 |
| 已是群成员 | 从 B 邀请已有群籍但未进房的队友；不要求退出重入群，不覆盖原角色，不创建第二条群籍。已有普通群邀请仍只入群，不应被自动导向 A。 |
| 错误接收者与失效 | 用另一账号尝试使用面向指定玩家的邀请，再以目标账号使用；前者不得入群或消耗目标玩家的邀请。分别测试管理员撤销、邀请人退出后重新入群、群解散。失败时不得泄露跨群房间资料或创建活动成员。 |
| 入房时重新校验 | 发出邀请后分别暂停、填满、删除 B，或修改房间密码。必须遵守当前资格、密码及容量；不能落入 A 或生成可用通道凭据。密码错误后仍留在原活动，正确密码走正常切房确认。 |

G 专项 `TC-ROOM-INVITATION` 使用两个产品页面、Rust 客户端和临时 PostgreSQL，覆盖注册前获邀、已注册非成员和已有管理员三种身份。常规 UI 错误恢复、复制内容和拒绝剪贴板的回退归入 `independent-first-use-browser`。完整回归另跑 `TC-LOCAL-REGRESSION`；不得用角色或权限的服务层通过替代桌面切房、外部打开邀请或玩家现场证据。

独立回归需覆盖真实控制面与数据库、桌面邀请入口以及进入活动后的查询；仅打开原型、仅跑群邀请测试或直接调用房间加入接口都不算端到端通过。正式玩家验证仍使用 `06a`，不向玩家提供房间列表位置或操作提示。

### 从应用外打开邀请：独立验收范围

- **发送与打开**：从成品房间页面取得可分享的链接；发给未安装或未登录的新玩家仍有安装后再打开、手动输入码的退路。已登录玩家不再经大厅输入邀请码。不能用测试注入房间 ID 或第二个空白桌面窗口代替现有窗口接管。
- **确认与切换**：分别从冷启动和已登录的运行中实例打开邀请，核对原账号、原活动、最终房间与占位。未确认、取消、错邮箱、密码错误或房间不可用均不得自动入房；其他模态操作进行中不可被异步邀请覆盖。
- **链接边界**：分享源来自客户端既定服务地址，不采纳邀请里的服务地址。页面 GET 不携带邀请码，不写入访问日志、浏览器持久存储或诊断。畸形链接不触发应用、核销或系统授权。相同页面连续打开不同片段也必须刷新/清除旧目标。
- **取证分层**：浏览器夹具证明呈现和确认，客户端与数据库证明身份及房间。另需核对 Windows 安装器注册和卸载清理，并在装好的候选版上从实际浏览器打开，记录系统提示和应用确认各几次。模拟事件、构建配置与未安装的 EXE 均不能代替最后一项。
