# 十二端 RTP 与播放回调同期观测

同机合成音测试复现了十二端播放卡顿。最后四个 15 秒窗口，132 个远端方向各收到约 50 个 RTP 包/秒，但原生回调只有 892～923 帧/窗，正常节拍应约为 1,500。远端观察期间 Rust 队列溢出为零；这次的缺口不能用少收同等比例的 RTP 包或该队列溢出来解释。这不是实际用户通话的根因结论，也不关闭此前语音与联机组合验收失败。

## 方法与边界

在 `scripts/local-preview/test-playout-cadence.py` 添加 `--rtp-stats`，沿用原 12 个发送端与 132 个接收方向。Rust 测试在共同单调时钟的窗口边界查询选定音轨；开启诊断才等待统一起点。每条音轨 8 个快照，发送端在最后一次查询结束后才停止。按方向与音轨校验快照唯一性、连续性和累计计数；包率使用同一 RTC 统计对象的时间戳差，查询完成时钟与耗时另列。边界并非逐包同步，独立快照运行最慢一次查询为 158.271ms。退出零只表示诊断完整，不表示音质通过。

固定 `synthetic`、受控音调、105 秒。不打开麦克风、不向系统扬声器播放、不运行网络 Helper；所有客户端在同一进程内共享 SDK。SDK 的 `packets_discarded` 有时比收到的包数增量还大，不作为线上丢包数；`packets_lost` 增量为零也不证明实际无损。没有测量每个包的音频内容或物理设备。

## 对照结果

首次采集的远端最差窗口有 1,497 个非静音帧，远端队列总计溢出 182 帧。按 SDK 时钟重算，接收包率 49.938～50.071 包/秒。独立源码快照则出现持续回调不足。两次均保留，未更改验收阈值。

第七窗 SDK 报告的 429,120 个采样折合约 894 个 480 采样帧，与接收端回调不足同时出现。两端报告非同时采集，不能以发送与接收包数相减判定单包丢失。发送侧诊断队列在第二窗也有溢出（端 3 为 161 帧），不要将远端零溢出外推至发送端或启动阶段。下一步优先区分共享播放泵驱动、解码和调度的影响，而不是扩大 Rust 队列；现有数据尚不能判定多进程或跨机通话也会出现此现象。
