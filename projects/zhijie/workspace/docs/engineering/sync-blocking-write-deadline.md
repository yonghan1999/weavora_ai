# 同步慢连接的阻塞写入期限

## 缺陷与修改

在 `8d954a9` 基线，生产 SyncService 对同一连接的回放、实时发送和关闭使用同一锁，保证顺序和注销后的旧引用隔离。但实际网络写入尚未设置应用期限，未读取的 TCP 对端可让注销后的 closeUser 等待当前发送，拖延清理和后续广播。此问题由真实回环 TCP/WebSocket 复现，不是 Mock 阻塞或推测历史百账号掉线原因。

SyncWebSocketHandler 现在在认证与回放前，经 Spring NativeWebSocketSession 取得 Jakarta Session，设置当前 Tomcat 的 `org.apache.tomcat.websocket.BLOCKING_SEND_TIMEOUT=2000L`。只收紧该连接单次阻塞写入至两秒，沿用原发送失败的注销、关闭和脱敏路径；未增加线程池、排队缓存、依赖或自定义重试，也未改变会话/群权限检查、游标确认、事件顺序、心跳或客户端恢复协议。

本机锁定 Tomcat 10.1.55 的实际 JAR 字节码表明阻塞发送读取该 Long 属性，缺省为 20,000 ms；实际修改前后的回归结果进一步验证该属性生效。不将 Jakarta AsyncRemote 的异步发送配置或并发装饰器误当当前 BasicRemote 阻塞写入的期限。

## 实际回归方法

`SyncSlowConsumerIntegrationTest` 使用临时 PostgreSQL 和生产 Spring/Tomcat，创建两个独立已验证账号及随机会话。一个正常 Java WebSocket 消费者持续读事件；另一个实际 TCP socket 以合法 WebSocket 握手连接，读取 101 完整头后不再读取，接收缓冲区设为 1 KiB。

测试经生产 SyncService 发送只向慢账号授权的、每条约 32 KiB 的合成传输探针，最多 512 条，逐条等待；实际写入超过 200 ms 未完成才认定 TCP 背压已经出现。这个大载荷不是产品群消息正文、容量模型或生产消息吞吐验收。随后调用真实 IdentityService.logout，事务返回后开始计时，要求生产 closeUser 在三秒内完成、当前发送结束、旧连接从注册表移除，并确认另一账号仍收到实际权威范围事件。

`SyncWebSocketHandlerTest` 同时验证属性在认证回放之前设置，防止仅实时发送受限而初始回放仍可长时阻塞。原会话退出/续期/过期、权限回放、提交顺序、Outbox 独立投递、脱敏诊断及真实 Rust 同步均需回归。

## 边界与原则

本修复只证明单条实际阻塞写入的有界退出与其连接锁清理，不把两秒当作所有场景的服务端撤销 SLA。广播仍串行，多个不同慢连接、积压事件、数据库延迟和全部通道联合五秒目标仍需更大范围验证。历史百账号握手失败、429 和发送告警没有因此判明或关闭；同机短测不能替代目标二核/2GB/5Mbit、一小时、实际媒体与跨机验收。
