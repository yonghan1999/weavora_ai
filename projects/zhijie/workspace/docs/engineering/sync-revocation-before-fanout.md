# 同步撤销先关闭目标连接

## 已复现的问题

`43245cc` 已限制单次原生 WebSocket 阻塞写入为两秒，但 `SyncRevocationTarget.deliver` 先向所有连接串行广播，再执行目标账号的 `closeUser`。因此多个互不相关的慢接收者仍能累积拖延目标账号关闭；单条写入有界不等于一次撤销有界。

新增真实网络回归使用临时 PostgreSQL、生产 Spring/Tomcat、两个独立 ACTIVE 账号及随机会话。目标账号由正常读取的 Java WebSocket 连接，另一账号建立三条实际 TCP/WebSocket 连接，读取合法 101 握手后不再读取。通过只向慢账号授权的约 32 KiB 合成探针，在真实发送超过 200 ms 未完成时确认背压，再调用生产 SyncRevocationTarget 投递包含目标账号的 `network.revoked` 事件。

修改前 `closed.get(5, SECONDS)` 实际超时。此夹具直接验证投递入口与真实网络关闭，不把合成探针当作产品消息容量模型，也不声称已覆盖真实业务事务提交至全部通道完成的五秒验收。

## 最小修复

只调整 `SyncRevocationTarget.deliver` 内部顺序：解析撤销事件并关闭目标账号现有连接后，再调用原有同步广播。普通事件、Outbox 确认时机、权限校验、游标推进、连接锁、严格串行发送和错误重试机制均不改变。未增加线程、异步队列、缓存、依赖或特殊重试。

无关接收者的慢写或广播异常不应成为目标撤销的前置条件。撤销目标不再依赖本次通知来主动断开，而是由服务端先行关闭。非法撤销载荷现在在广播前失败，仍抛出原有脱敏异常，不确认该事件；无 user_id 或值为 null 的既有行为不变。

## 尚未证明的边界

此改动只解决已经进入 SyncRevocationTarget 的目标关闭被无关接收者广播拖延的问题。排在更早 Outbox 事件之后、调度器被占用、目标自身多条慢连接、数据库等待或全部通道联合撤销，仍可能超过五秒。广播本身仍串行，慢接收者仍可能拖延其他账号收到事件；没有将目标连接本机约 2 ms 的结果写成全局 SLA。

Windows 试用包已另行从干净归档构建并验证，详见下节；不将源码测试替代制品实跑。目标服务器容量、实际跨机虚拟网络、音频、三平台安装签名及 F/G/H/I 和人工审批仍未完成。

KISS/YAGNI：使用现有关闭入口，只重排必要操作。DRY：三种撤销复用同一投递路径，真实网络握手夹具复用一个方法。单一职责：撤销入口负责先终止目标连接，原广播继续负责通知当前授权接收者。
