# 外部撤销通道并行与独立提交

## 问题与范围

继续补齐原架构中语音、网络撤销互不阻塞的要求，不修改五秒目标或扩大批准范围。前轮已隔离同步与外部投递，但 SFU 与 Relay 仍共用一条外部任务及批次事务，任一通道阻塞都会推迟另一通道调用和完成状态提交。

`ExternalRevocationChannelIntegrationTest` 使用真实 Spring、PostgreSQL 和实际定时器，以闩锁确认一个外部目标已经进入且未释放，再记录另一通道事件。修复前，后一通道在三秒内未得到投递，断言失败。回执端点仅为本机 HTTP 夹具，不是实际媒体通话。

## 实现

- `ExternalDeliveryChannel` 将 `voice.revoked`、`network.revoked` 与其余事件分成三个不重叠分区。SQL 在一百条批次限制前过滤通道，避免另一通道积压占满查询结果；仍要求同步完成、整体未完成及重试已到期。
- `ExternalRevocationSchedule` 每个分区各登记一条 fixed-delay 任务，共用固定三线程的专用外部调度器。每条任务串行执行自己的批次；没有按事件创建线程、无界提交队列或扩大默认业务调度器。
- 调度入口调用受 Spring 代理的 `ExternalRevocationDispatcher`，每通道有独立事务，不共享一个横跨语音和网络调用的外层事务。默认同步调度仍单线程；游标分配仍在独立短事务中提交，不在网络调用期间持有分配锁。
- 保留 V16 的持久化退避、到期时间与同步序号排序、失败计数、固定脱敏告警及实际失败语义。没有新依赖、数据库迁移或配置开关；未配置 SFU/Relay 时仍不能把事件标为成功。

手动 `RevocationDispatcher.dispatchPending()` 保留同步返回计数的组合入口，依次调用三个受代理分区，不承担生产并行调度承诺。独立调度职责、共用派发实现和固定分区遵循单一职责、DRY、KISS、YAGNI。

## 限制与运行边界

这里只证明单个控制面进程的跨通道调度及事务隔离，不是跨进程派发独占或严格一次投递。同一通道内仍顺序处理，有长积压或多个慢请求时不能承诺五秒内清空；共享数据库、连接池及资源耗尽也不在隔离保证内。新增通道若需要独立隔离，必须明确扩展分区和固定调度，不能将所有扩展目标视为已互相隔离。

没有启动原生桌面、安装驱动、修改防火墙或触碰既有试用数据。人工试音继续搁置；真实媒体/TUN 失权、跨机与三平台、目标服务器容量和许可证人工审核仍未完成。Relay 仍保留权威验证与有界 deny，不是完整授权缓存。已有 `e45156f` 试用包不包含本轮通道隔离变更。

所有新增缓存、临时数据库及构建输出均在 D 盘，只设置当前进程环境；测试完成后只清理本轮确认无用的临时目录，保留日志、制品、共享缓存及源码，不重试历史被拒清理路径。
