# 同步恢复后及时更新服务状态

## 缺陷复现

`d59a005` 的断链联调允许消息恢复后继续等待下一次 presence 心跳，长失联恢复为 14,971 ms，接近十五秒检查上限。生产同步循环在连接成功及事件处理成功时均不恢复 `core.service`；UI 对 Retrying 显示服务暂不可用，即使消息通知与真实 HTTP 读取已经恢复，该状态仍可能保留到下一次十五秒维护周期。

先在真实生产后台循环夹具增加断言：收到离线消息通知并用当前凭据实际读到该消息后，服务必须已为 Connected，不能再等待心跳。未修改产品实现时，短失联用例实际失败，Rust 明确报告实际 Retrying、期望 Connected。失败日志、子进程诊断及 XML 保留在 Git 忽略的 `target/sync-service-recovery-d59a005/`：`before.log`、`before-rust.log`、`before-report.xml`。`before.log` SHA-256 为 `36f43882b191018a92952c125097f9d0a97a085ae73149856a295eac00d7e31f`，不是把夹具问题推定为产品缺陷。

## 修复边界

同步连接成功后取得既有 `activity_operations` 操作锁，再次核对当前访问凭据，只为仍绑定当前会话的结果恢复服务状态，然后发送已有的全量刷新通知。成功处理合法事件时，在既有操作锁及凭据核对之后同样恢复状态，再确认游标并通知 UI。连接建立只作为服务可达信号，不替代后端身份校验；不改变凭据、活动资格、租约、IP、心跳周期、超时或自动刷新策略。

旧凭据的连接成功结果不能修改新会话；等待操作锁期间发生凭据旋转也必须丢弃旧结果。注销后不得重新标记 Connected。事件失败或已过期会话的事件不能确认游标，原撤销与本地清理语义不变。不在测试中强制恢复状态、不缩短生产心跳，也不放宽十五秒限制。
