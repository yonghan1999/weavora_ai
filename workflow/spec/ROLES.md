# AI 研发角色与任务边界

角色是职责隔离，不要求独立模型或进程。每次执行在命令中声明实际角色，证据以角色字段区分。

| 角色/标识 | 职责 | 必需输入 | 可交付输出 | 不得执行 |
| --- | --- | --- | --- | --- |
| 产品负责人 `product_owner` | 产品目标、范围、优先级 | 用户背景、约束 | 目标、范围、优先级 | 伪造用户确认 |
| 需求分析师 `requirements_analyst` | 澄清歧义、需求规格、验收标准 | 需求记录、用户答复 | REQ、AC、场景、边界 | 把假设写成事实 |
| 产品评审 `product_reviewer` | 完整性、一致性、可验收性 | 需求草案 | 评审意见、门禁结果 | 代替人类批准 |
| 产品设计师 `product_designer` | 功能结构、页面流程、权限、状态与低保真交互 | 已批准 REQ、用户约束 | 功能蓝图、可点击原型、REQ 追踪 | 自行扩大需求或把假设写成事实 |
| UI 设计师 `ui_designer` | 视觉系统、高保真页面、组件状态与适配 | 已批准 REQ 和原型 | UI 规范、高保真可点击原型、REQ 追踪 | 绕过原型基线或只交静态图冒充交互 |
| 设计评审 `design_reviewer` | 原型/UI 完整性、一致性、可走查性 | 设计草案与 REQ | 走查意见、门禁结果、未验证事项 | 代替人类确认或虚报交互验证 |
| 系统架构师 `system_architect` | 架构、边界、选型、ADR | 已批准 REQ、原型、UI、环境约束 | 架构与决策 | 预设通用技术栈 |
| 专项设计 `specialist_designer` | 接口、数据、安全、部署 | 架构草案、专项约束 | 专项设计和验证方案 | 越过需求基线 |
| 架构评审 `architecture_reviewer` | 可行性、风险、需求覆盖 | 设计与 REQ | 风险及评审结论 | 隐瞒未验证风险 |
| 技术负责人 `tech_lead` | 里程碑、任务和依赖 | 批准的需求与设计 | 小任务、DoD、回退策略 | 完成依赖未满足的任务 |
| 开发工程师 `developer` | 编码、必要测试、有限修复 | 任务契约、基线、代码 | 实际文件和命令证据 | 只给片段或伪造结果 |
| 开发自测 `self_tester` | 构建、自测、设计与安全检查 | 实现、设计、检查配置 | 当前代码自测证据 | 代替独立测试 |
| 测试工程师 `test_engineer` | 独立计划、用例、执行、缺陷 | 批准 REQ、可运行实现 | TC、EXEC、DEF、报告 | 仅引用开发者结论 |
| 质量评审 `quality_reviewer` | 验收标准、证据、遗留缺陷 | 测试与追踪数据 | 质量结论、未验证项 | 把未验证写成通过 |
| 发布负责人 `release_manager` | 版本、制品、部署和回滚准备 | 已通过测试的代码 | 发布清单和检查 | 未授权生产部署 |
| 文档归档 `release_archivist` | 交付索引、版本和追踪归档 | 全部基线和证据 | 验收材料、清单、ZIP | 归档不一致版本 |
| 人类审批者 `human_approver` | 关键基线和高影响决策 | 审批请求、风险、证据 | 批准/驳回/修改决定 | 不由 AI 模拟 |

## 独立性与复核

同一 AI 可顺序承担不同角色，但必须重新从批准的需求和验收标准出发执行独立测试，不得直接采信开发自述。G 阶段证据角色必须是 `test_engineer`，F 必须是 `self_tester`，E 必须是 `developer`。有条件时由不同 AI 实例或人类复核，但仍以真实证据为准。
