# 工具无关研发工作流规范

## 1. 目标与边界

本规范定义需求到归档的控制平面，不规定业务项目的语言、框架、数据库、架构或部署平台。业务代码位于各项目 `workspace/`，工作流代码与业务技术决策分离。

## 2. 阶段与出口

| 阶段 | 主要产出 | 出口条件 |
| --- | --- | --- |
| A 需求接收 | 原始需求、已知条件、问题、初略范围风险 | 记录生成后进入需求分析 |
| B 需求分析 | 需求规格、场景、验收标准、REQ 标识 | 门禁通过，人类批准需求基线 |
| B1 产品原型设计 | 功能清单、页面结构、核心流程、权限与异常状态、可点击低保真原型 | REQ—原型追踪完整，本地链接有效，人类批准原型基线 |
| B2 UI 视觉设计 | 视觉规范、高保真页面、组件状态、响应式与可访问性、可点击 UI 原型 | REQ—UI 追踪完整，原型与本地链接有效，人类批准 UI 基线 |
| C 架构设计 | 架构、选型、接口、数据、安全、部署、ADR | REQ 全覆盖，人类批准设计基线 |
| D 开发规划 | 里程碑、任务、依赖、完成定义、回退 | 任务持久化且 REQ—TASK 可追踪 |
| E 编码实现 | 代码、自动化测试、任务执行证据 | 所有任务完成，证据退出码为 0 |
| F 开发自测 | 自测报告、构建和测试证据 | 必需检查由 self_tester 对当前代码通过 |
| G 独立测试 | 计划、用例、报告、缺陷与回归证据 | REQ 全覆盖；test_engineer 通过；无开放缺陷 |
| H 发布准备 | 版本、制品哈希、部署、回滚、发布检查 | 版本和制品一致；test_engineer 对最终工作区回归通过；人类批准发布准备 |
| I 验收归档 | 验收报告、交付索引、归档清单和 ZIP | 人类最终验收，归档门禁通过 |

生产部署不在默认工作流内。任何生产发布、生产数据修改、不可逆操作或高影响外部操作均须另行明确授权。

## 3. 状态机

状态：`pending`、`in_progress`、`awaiting_approval`、`approved`、`rejected`、`failed`、`awaiting_retry`、`blocked`、`paused`、`cancelled`、`completed`。合法迁移由 `workflow/config/state_machine.json` 唯一约束，执行器拒绝越权迁移。

- `submit` 仅接受 `in_progress`，先运行门禁；需审批时进入 `awaiting_approval`，否则自动进入下一阶段。
- `approved` 是审计中可追踪的瞬时状态，随后进入下一阶段或 `completed`。
- 人工驳回进入 `rejected`，用 `revise` 修改后可重新提交，新旧审批均保留。
- 命令失败进入 `awaiting_retry`；`retry` 有有限次数，耗尽进入 `blocked`。
- `pause` 保存恢复前状态；`resume` 读取 JSON 状态恢复，不依赖对话记忆。
- `cancelled` 和 `completed` 是终态。

## 4. 审批协议

B、B1、B2、C、H、I 为默认人工门禁。审批请求包含阶段、事项、文档路径、基线摘要哈希和可选决定。只有人类执行带明确确认值的 `approve` 命令才产生 `explicit_human_cli` 记录；AI 不得执行该命令或编辑审批记录。

B1 必须先于 B2 完成，禁止用高保真外观掩盖未确认的功能与流程。两阶段入口分别为 `workspace/design/prototype/index.html` 和 `workspace/design/ui/index.html`，使用模拟数据，不连接生产服务。自动门禁检查文档结构、REQ 追踪、交互元素和本地链接；完整操作路径须由人工走查，未实际验证的浏览器、设备或交互不得写成已通过。

批准绑定当前基线 SHA-256。文档、原型、UI、任务、测试或发布清单在审批后变化，旧审批失效，必须重新提交。当前审批请求必须与归档请求一致，后续门禁同时核对状态中的批准记录和独立决策文件。B2 基线包含需求与 B1 原型，C 及最终交付基线包含需求、原型与 UI，确保后续变更可检测。H 的批准只表示发布材料就绪，不授权生产部署。

`workflow_version: 2` 的新项目启用 B1/B2。未声明该版本的既有项目保持创建时的九阶段路径，避免新规则追溯性地使在途审批失效；迁移既有项目须另行明确决定，不得直接编辑状态或审批记录。

## 5. 执行与证据

- 开发任务和检查通过 `task-run`、`verify` 在对应项目 `workspace/` 真实执行；任务命令必须与登记的 `test` 一致，执行角色由阶段强制约束。
- 每次执行保存命令、角色、时间、退出码、截断后的标准输出和标准错误、截断标志、超时标志及代码树哈希。
- 自然语言自述不是完成证据。完成任务的最近证据必须退出码为 0，证据文件 SHA-256 与任务/检查/用例记录一致，且证据标识、项目、命令和上下文匹配。
- F/G/H 证据绑定当前代码树和对应阶段；代码变化或证据完整性校验失败后必须重跑必要测试和回归。
- 超时终止进程树，输出分别最多记录 1,000,000 字节；执行器不是操作系统安全沙箱。
- G 失败用例自动创建 DEF 缺陷和 FIX 修复任务；通过后记录解决证据。

## 6. 持久化与恢复

每个项目独立保存 `state.json`、`audit.jsonl`、任务、审批、执行证据和文档。写入采用同目录临时文件原子替换，项目锁避免并发修改；框架元数据操作使用项目级回滚日志，异常或崩溃后在下次带锁访问时恢复，新项目创建中断可安全重试。外部命令副作用和业务工作区文件不由日志回滚。中断后使用 `status` 查看，再按状态选择 `resume`、`retry`、`revise` 或人工审批。

## 7. 范围变更

已批准需求或设计发生重大变化时，由人类决定新基线。AI 可准备修改，但不得把原审批沿用到变化后的摘要。重大成本、安全、合规和不可逆决策必须暂停并请求人工介入。
