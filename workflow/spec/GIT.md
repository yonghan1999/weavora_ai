# Git 提交、推送与版本记录规则

## 1. 基本原则

- **本地 commit 与远程 push 是两件事。** commit 用于保存已验证、可恢复的逻辑节点；push 会改变远程仓库，必须单独授权。
- 不按文件保存次数、命令执行次数或时间间隔提交，不在未验证、待审批或失败状态形成“完成”提交。
- 一个提交只包含一个逻辑变更，代码、对应测试、任务状态和证据索引尽量在同一提交中。
- 用户明确给出的临时提交、分支或推送指令优先，但不得绕过安全检查和人工审批。

## 2. 默认提交时机

| 工作流节点 | 何时本地提交 | 提交内容 |
| --- | --- | --- |
| 工作空间初始化 | 基础文件真实创建且验证通过，用户要求纳入仓库时 | 工作流、模板、测试和初始化报告 |
| A–B 需求基线 | 用户批准 B 后 | 原始需求、需求规格、审批记录和状态 |
| C 设计基线 | 用户批准 C 后 | 架构、专项设计、ADR、审批记录和状态 |
| D 开发规划 | 任务、依赖和追踪门禁通过后 | 开发计划和任务数据 |
| E 编码实现 | 每个任务完成且对应命令证据通过后；强关联小任务可组成一个逻辑提交 | 实现、测试、任务状态及证据 |
| 缺陷修复 | 一个缺陷修复且相关测试与必要回归通过后 | 修复、回归测试、缺陷状态和证据 |
| F 开发自测 | 自测门禁通过后 | 自测报告、检查配置和证据 |
| G 独立测试 | 独立测试门禁通过且无开放缺陷后 | 用例、报告、缺陷记录和测试证据 |
| H 发布准备 | 用户批准发布准备后 | 发布文档、制品清单、最终回归证据和审批记录 |
| I 验收归档 | 用户最终验收且归档检查通过后 | 验收报告、交付索引、归档结果和状态 |
| 工作流自身维护 | 一个逻辑维护变更完成且全部相关测试通过后 | 对应代码、测试和文档 |

不为了凑节点重复提交；如果某阶段没有文件变化，不创建空提交。

## 3. 默认不提交的情况

- 需求或设计仍在待审批、已驳回或要求修改状态。
- 构建、静态检查或适用测试失败，或结果无法验证。
- 任务依赖未完成、存在开放缺陷或临时占位实现。
- 变更混入无关文件、其他任务、临时缓存、密钥或大体积生成物。
- 尚未检查差异，或提交会把未授权范围变化写成已完成。
- 仅在本地试验、排查或生成中间结果。

确需保存未完成工作时，须由用户明确要求 WIP 提交，使用 `wip:` 前缀且默认不推送；不得将 WIP 标记为完成或发布。

## 4. 每次提交前检查

1. `git status --short` 和暂存差异：只包含本节点相关文件。
2. 当前阶段、审批和任务状态：与提交说明一致。
3. 适用门禁、构建和测试：真实通过，证据存在。
4. 密钥与隐私：无 `.env`、令牌、密码、私钥或不应公开的信息。
5. `git diff --cached --check`：无空白错误等基础问题。
6. 仓库本地身份：当前仓库使用 `han <yong.han.life@outlook.com>`；不修改全局身份。
7. 提交后核对提交号、作者和文件清单，并保留工作区状态。

不得使用 `--no-verify` 绕过钩子，不用提交来掩盖失败检查。

## 5. 提交说明

采用 `<type>(<scope>): <summary>`，一个逻辑变更一条简洁说明：

- `docs(requirements): approve initial requirement baseline`
- `docs(architecture): approve core network and voice design`
- `feat(TASK-001): implement room membership admission`
- `fix(DEF-TC-001): revoke stale room session credentials`
- `test(G): add cross-room isolation regression`
- `chore(release): prepare version 0.1.0`

提交说明只描述已实际完成和验证的内容，不写“全部通过”“已兼容”或“已发布”等无证据结论。

## 6. 推送、分支与标签

- 经用户确认本规则后，AI 可在第 2 节节点执行**本地 commit**，无需每次另行询问；未确认前仍逐次授权。
- **push 始终需要用户明确指令或另行建立的持续推送授权**；本地 commit 不隐含 push 授权。
- 不自动创建、切换、合并、变基或删除分支，不自动修改默认分支。
- 禁止自动 force push、hard reset、删除远程分支或覆盖他人提交。
- 发布标签只在版本和发布动作获明确授权后创建；发布准备批准不自动等于打标签或生产发布。
- 推送前检查远程变化，必要时先安全整合；推送后核对远程分支提交号。
