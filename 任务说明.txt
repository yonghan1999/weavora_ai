# 任务：初始化通用 AI 自主软件研发工作空间

## 1. 你的任务

你需要将当前打开的项目目录，实际初始化为一套可复用、可执行、可恢复、具备人工审批机制的通用 AI 软件研发工作空间。

这不是一个具体的软件业务项目，而是一套能够帮助 AI 持续完成软件研发工作的通用框架。

初始化完成后，我希望能够在项目中提出一个软件需求，由 AI 按照既定工作流逐步推进：

需求接收 → 需求分析 → 产品设计 → 需求评审 → 架构设计 → 架构评审 → 开发规划 → 编码实现 → 开发自测 → 独立测试 → 缺陷修复 → 发布准备 → 交付验收 → 归档。

其中，关键决策由我审批，其余可以自动执行的工作由 AI 自主推进。

**你的核心交付不是一份设计方案，而是已经在当前目录中创建完成、经过实际验证、能够开始使用的工作流框架。**

请直接执行初始化任务，不要只告诉我应该如何做。

## 2. 通用约束

### 2.1 不预设未来项目的技术栈

本框架服务于不同类型的软件项目。

不得在初始化阶段预先规定未来项目必须使用：

- Java、Python、JavaScript 或其他特定编程语言。
- 某种固定的前端或后端框架。
- 某种固定数据库。
- 某种固定部署平台。
- 某种固定的软件架构。
- 某种固定的业务领域。

当未来收到具体需求时，应由 AI 根据需求、运行环境、维护成本、性能要求、安全要求和团队约束决定技术方案。

通用研发工作流本身可以使用合适的工具实现，但必须将工作流基础设施与未来业务项目的技术决策分离。

### 2.2 不绑定特定 Coding Agent

你当前使用的 Coding Agent 只是执行本次初始化的工具，不代表未来必须使用相同工具。

先检查当前环境能够提供的能力，例如：

- 读取和修改文件。
- 执行命令和测试。
- 调用 AI 模型或其他 Agent。
- 读取执行结果及错误信息。
- 保存任务状态和执行记录。
- 暂停并等待人工审批。
- 在中断后恢复工作。

根据实际能力选择合适的实现方式。

优先建立工具无关的工作流定义、任务契约、状态模型和文档规范，再通过适配层对接具体的 Coding Agent。

如果当前环境不支持某项能力，应明确标记为待接入或需要人工操作，不得伪造执行结果。

### 2.3 遵循最小可行实现原则

优先建立一套能够真正跑通完整研发流程的最小可行版本。

不要为了追求架构完整而过度设计，也不要在没有必要的情况下引入复杂的分布式系统、微服务、消息队列、数据库集群或多 Agent 调度平台。

先保证流程可用、状态可靠、产物完整、审批有效、执行可追踪，再考虑扩展。

## 3. 第一步：检查当前环境

开始创建文件前，先检查：

1. 当前工作目录及已有文件。
2. 是否存在 Git 仓库。
3. 是否存在已有项目规则和 Agent 配置。
4. 可用的运行环境、命令行工具及测试能力。
5. 当前 Agent 的实际权限与执行限制。
6. 是否存在可能被覆盖的内容。

对已有文件进行保护。

如果发现与本任务冲突的用户配置，不得擅自删除或覆盖；应保留原内容并采用兼容方式整合，或者在确实存在风险时请求我确认。

完成检查后，简要说明你的实施计划，然后继续执行。不要等待我确认普通的实现细节。

## 4. 第二步：建立研发角色体系

建立清晰的 AI 角色定义，至少包括：

### 产品与需求阶段

- 产品负责人：维护产品目标、范围和优先级。
- 需求分析师：澄清需求、识别歧义、编写需求文档。
- 产品评审角色：检查需求完整性、一致性、可验收性。

### 设计阶段

- 系统架构师：负责总体架构、模块边界和技术方案。
- 专项设计角色：根据实际项目需要负责接口、数据、安全、部署等设计。
- 架构评审角色：检查设计的可行性、风险和需求覆盖情况。

### 实施阶段

- 技术负责人：制定实施计划、分解任务、管理依赖。
- 开发工程师：执行具体编码任务。
- 开发自测角色：检查实现正确性、构建结果和单元测试。

### 质量阶段

- 测试工程师：制定测试计划、测试用例并执行验证。
- 质量评审角色：核验验收标准、测试证据和未解决缺陷。

### 交付阶段

- 发布负责人：检查发布准备、版本信息、部署及回滚方案。
- 文档与归档负责人：整理交付物、追踪关系和版本归档。

这些角色可以由一个或多个 AI 实例承担，不要求每个角色对应独立模型或进程。

必须通过明确的角色职责、输入输出契约和任务边界避免角色混乱。

独立测试与质量评审应尽可能避免仅依赖开发者自己的结论，但不必为每个角色创建独立 AI 进程。

## 5. 第三步：建立标准研发工作流

将工作流定义为明确的状态机，而不只是写在说明文档中的流程图。

至少包含以下阶段：

### 阶段 A：需求接收

输入：用户提出的初始想法、目标、限制和背景信息。

输出：

- 需求记录。
- 当前已知条件。
- 待澄清问题。
- 初步范围及风险。

规则：

- 不得将未经确认的假设当成用户已确认的事实。
- 对影响业务目标、范围、合规性或验收结果的重要歧义，必须询问用户。
- 非关键细节可以记录合理假设后继续。

### 阶段 B：需求分析

输出：

- 需求规格说明书。
- 用户故事或使用场景。
- 功能需求和非功能需求。
- 业务流程及关键状态。
- 异常场景与边界条件。
- 验收标准。
- 需求追踪标识。

规则：

- 需求必须具有唯一标识。
- 每项重要需求都应具备可验证的验收标准。
- 对冲突、不可行或高风险需求提出明确意见。
- 文档生成后必须进行完整性检查。

门禁：等待用户批准需求基线。

### 阶段 C：架构与详细设计

输出：

- 架构设计文档。
- 技术选型及其依据。
- 模块划分与职责。
- 核心数据模型。
- 接口契约。
- 安全与权限设计。
- 部署及运行方案。
- 技术风险和待验证事项。
- 关键技术决策记录。

规则：

- 技术选型必须基于当前具体项目，而非本框架预设的固定技术栈。
- 对关键技术风险优先设计验证方案。
- 架构和接口必须能够追溯到已批准的需求。

门禁：等待用户批准设计基线。

### 阶段 D：开发规划

输出：

- 开发里程碑。
- 可执行任务列表。
- 任务依赖关系。
- 每项任务的输入和输出。
- 完成定义及验收标准。
- 测试要求。
- 风险和回退策略。

规则：

- 任务应尽量小、边界明确、可以独立验证。
- 依赖未完成的任务不得被标记为完成。
- 能够安全并行的任务可以并行，否则按依赖顺序执行。
- 生成的任务必须实际写入项目文件或持久化状态存储。

### 阶段 E：编码实现

开发 Agent 按任务执行：

1. 读取相关需求、设计和任务说明。
2. 检查当前代码与已有实现。
3. 制定本任务的实现计划。
4. 修改或创建实际代码文件。
5. 编写必要的自动化测试。
6. 运行构建、静态检查和适用的测试。
7. 分析失败原因并进行有限次数的自动修复。
8. 保存代码变更和执行证据。
9. 更新任务状态。

不得仅输出代码片段或伪造构建结果。

如果无法执行某项检查，必须记录原因并将其标记为未验证。

### 阶段 F：开发自测

检查：

- 代码能否构建或运行。
- 自动化测试是否通过。
- 主要异常和边界条件是否得到处理。
- 是否违反已批准的设计。
- 是否引入明显的安全风险。
- 是否存在未完成实现或临时占位代码。

失败时返回开发阶段修复。

### 阶段 G：独立测试与质量验收

根据已批准的需求及验收标准生成测试计划。

至少覆盖适用的：

- 功能测试。
- 边界条件测试。
- 异常处理测试。
- 集成测试。
- 回归测试。
- 安全性与权限测试。
- 性能和兼容性测试。

实际测试范围应根据项目类型确定，不适用的项目不得机械套用所有测试类别。

输出：

- 测试计划。
- 测试用例。
- 实际执行记录。
- 失败用例和缺陷单。
- 需求覆盖情况。
- 测试报告。

缺陷应关联需求、任务和复现步骤。

失败后自动创建修复任务，在修复完成后重新执行相关测试及必要的回归测试。

当重试次数耗尽、出现无法判断的结果或需要修改已批准的需求时，暂停并请求人工介入。

### 阶段 H：发布准备

输出：

- 发布版本及变更说明。
- 构建产物或制品获取方式。
- 部署和配置说明。
- 数据迁移方案（适用时）。
- 安全检查结果。
- 已知问题列表。
- 回滚或恢复方案。
- 发布检查清单。

规则：

- 默认只准备发布，不擅自部署到生产环境。
- 正式发布、生产数据修改、不可逆操作以及涉及外部用户的高影响操作，必须取得明确授权。
- 不得将未经验证的构建产物标记为可发布。

### 阶段 I：最终验收与归档

输出完整交付包，至少包括：

- 已批准的需求基线。
- 架构及技术决策文档。
- 开发任务清单和完成情况。
- 代码版本或提交标识。
- 构建与测试证据。
- 缺陷处理记录。
- 发布说明。
- 部署与回滚说明。
- 已知问题和遗留风险。
- 最终验收报告。
- 交付物索引和版本信息。

归档前检查交付物是否齐全、版本是否一致、证据是否真实可追溯。

未满足必要质量门禁时，不得生成“全部通过”的结论。

## 6. 第四步：实现工作流状态机

为工作流定义明确的状态、迁移条件和异常处理机制。

至少支持：

- 待开始。
- 执行中。
- 待人工审批。
- 已批准。
- 审批驳回。
- 执行失败。
- 等待重试。
- 被阻塞。
- 已取消。
- 已完成。

具体状态可以根据实现需要细化，但必须防止不合法的状态迁移。

每次状态变化应记录：

- 工作流及任务标识。
- 原状态和目标状态。
- 操作时间。
- 执行角色。
- 变更原因。
- 关联的产物或证据。
- 是否需要人工授权。

审批状态必须由实际的人工确认行为触发，不能由 AI 自己将“待审批”修改为“已批准”。

被驳回的任务必须保留原因和修改记录，并支持重新提交审批。

工作流应支持暂停、恢复和失败恢复。中断后应能读取持久化状态，而不是依赖之前对话仍然存在。

## 7. 第五步：实现人工审批机制

采用以下默认策略：

### 必须人工审批

1. 需求基线。
2. 架构与关键技术方案基线。
3. 超出已批准范围的重大需求变更。
4. 涉及重大成本、数据安全、合规性或不可逆影响的决策。
5. 正式生产发布。
6. 最终交付验收。

可以根据风险为其他阶段增加审批点。

### 自动推进

在已经批准的范围内，以下工作默认自动执行：

- 文档生成和检查。
- 任务拆解。
- 编码实现。
- 构建与自动化测试。
- 常规缺陷修复。
- 回归测试。
- 质量报告生成。
- 交付文档整理。

审批请求必须提供：

- 当前审批阶段。
- 需要审批的具体事项。
- 方案摘要及重要决策。
- 相关文档路径。
- 风险和影响。
- 验收标准及检查结果。
- 可选择的批准、驳回或要求修改等操作。

如果当前 Coding Agent 不具备交互式审批能力，应实现明确的暂停状态和可由用户操作的审批文件或命令入口。

不得通过自动创建一个默认“批准”文件来绕过人工审批。

## 8. 第六步：建立统一的项目文件结构

根据实际执行环境调整目录，但必须覆盖以下职责：

- 项目总规则和使用说明。
- 工作流定义与状态机。
- Agent 角色定义。
- 输入输出契约。
- 研发文档模板。
- 质量门禁和验证脚本。
- 需求记录。
- 架构设计与决策。
- 开发任务与依赖。
- 测试计划、用例和执行记录。
- 缺陷追踪。
- 发布准备与交付归档。
- 运行状态与审计记录。
- 工具适配及使用说明。

建议以职责划分目录，不要将所有内容堆在一个大型提示词中。

根目录应包含一份简明的使用指南和适用于当前 Coding Agent 的项目规则文件。

同时提供一份工具无关的核心规范，避免整个工作流只能在某一种 Agent 中运行。

所有模板都应有清晰的填写要求，必要时包含示例，但不能把示例误认为真实项目数据。

## 9. 第七步：建立统一的 Agent 输入输出契约

每个角色的任务至少需要定义：

### 输入

- 工作流标识。
- 任务标识。
- 当前阶段。
- 任务目标。
- 已批准的需求与设计基线。
- 相关文件和上下文。
- 约束及禁止事项。
- 验收标准。
- 可用工具与权限。

### 输出

- 执行结果。
- 实际创建或修改的文件。
- 关键决策及其依据。
- 执行过的命令和检查。
- 测试结果及证据。
- 未完成事项。
- 风险和阻塞原因。
- 建议的下一步操作。
- 推荐的状态迁移。

输出状态必须区分：

- 已完成并验证。
- 已完成但未验证。
- 部分完成。
- 执行失败。
- 等待人工决策。

不得仅凭 Agent 的自然语言自述认定任务成功。可验证的结果应以文件、命令返回结果、测试报告、版本标识或其他真实证据为依据。

## 10. 第八步：实现质量门禁

将关键门禁落实为可执行的检查程序或可验证规则，而不是只写在文档里。

至少实现以下检查：

1. 需求文档必需章节检查。
2. 需求唯一标识和验收标准检查。
3. 需求、设计、任务和测试之间的追踪检查。
4. 任务完成条件检查。
5. 必要构建和自动化测试检查。
6. 审批状态检查。
7. 发布交付物完整性检查。
8. 归档版本一致性检查。

根据当前环境选择合理实现方式，例如脚本、结构化数据校验、Git 检查或工作流执行器。

如果某项检查需要依赖未来项目才能确定，应提供可扩展的检查接口，并明确记录它目前无法完整验证的原因。

禁止以“文档中写了检查要求”代替真正可执行的门禁。

## 11. 第九步：实现工作流入口

初始化完成后，我应当知道如何开始一个新的软件研发项目。

请提供清晰的入口，例如：

- 创建新研发项目。
- 提交一个新需求。
- 查看当前阶段和任务状态。
- 查看待审批事项。
- 批准或驳回当前阶段。
- 恢复中断的工作流。
- 重试失败任务。
- 查看测试报告。
- 生成交付归档。

根据当前环境选择最适合的实现形式。

可以使用命令行、结构化任务文件、Agent 工作流指令或其他可执行机制，不强制要求开发独立 Web 界面。

但至少应当实现一个真实可用的启动方式，以及清晰的人工审批和恢复方式。

如果底层 Coding Agent 只能在交互会话中工作，应明确哪些步骤需要用户重新调用 Agent，不能声称已经实现后台自主运行。

## 12. 第十步：必须进行端到端验证

创建文件后，不要立即宣布完成。

必须实际检查初始化结果，并执行当前环境能够完成的验证。

至少包括：

### 基础验证

- 检查目录和必需文件是否存在。
- 检查配置和模板格式。
- 检查工作流定义是否完整。
- 检查状态迁移规则是否合法。
- 检查入口指令是否能够正确触发流程。
- 检查审批机制是否能够阻止越权推进。

### 工作流验证

建立一个隔离的临时测试项目或测试工作流，模拟一个最小的软件需求。

验证它能够：

1. 接收需求并生成需求文档。
2. 到达需求审批节点并暂停。
3. 在明确批准后继续。
4. 生成架构设计和开发任务。
